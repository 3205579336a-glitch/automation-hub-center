# Purchasing Automation Hub Agent Bridge

The Agent Bridge accepts one action, `QUERY_APQP_PLANNED_DATES`. The demo uses an in-memory queue and Fake SAP. Phase 2 adds a Graph queue adapter tested with a mock transport. The standard Hub does not instantiate that adapter or start polling.

## Run the offline demo on Windows

From a new PowerShell window, use the feature worktree or replace the path with your checkout of `codex/copilot-agent-bridge`.

```powershell
Set-Location -LiteralPath "$env:USERPROFILE\Desktop\automation-hub-copilot-bridge"
npm.cmd ci
py -3 -c "import pythoncom, win32com.client, win32con, win32gui"
npm.cmd run demo:pah-agent
```

If the Python import check reports missing modules, run `py -3 -m pip install pywin32` before starting the demo. Dependency installation may download packages. With dependencies installed, the demo runs without network access, SAP GUI, Microsoft Graph, SharePoint or tenant credentials.

The console shows submission, request and operator validation, a queue claim, the native APQP query against Fake SAP, result writeback and the persisted Hub history entry. It prints one sample record and the paths to `queue-result.json` and `execution-history.json` in a new temporary folder. The demo checks that all 25 fixture records were returned, the job/run/history IDs agree and the native trace records one query with zero write events. The desktop approval is synthetic and lives only in the demo process.

## Existing architecture and bridge changes

| Area | Existing safeguard | Bridge integration |
| --- | --- | --- |
| Electron main and IPC | `src/main/index.ts` takes Electron's single-instance lock and builds the trusted main-process services. IPC verifies the renderer before accepting APQP requests. Hub shutdown requests a cooperative stop before exiting an active guided run. | Extracted the APQP query operation from IPC. The same operation instance is available in main for the renderer and the optional worker. |
| Guided automation | `GuidedAutomationService.begin()` holds one run at a time and checks external blockers, including RFQ recovery and history cleanup. Local interaction requests are owned by the active run and validate request IDs and allowed responses. | The worker holds this lock from claim through the read and local result checkpoint. A busy Hub leaves the item queued. The worker has no channel for submitting interaction responses. |
| APQP date query | `ApqpDateService` validates engine records, field schema and VCE/100. `ApqpRunner` shares process exclusion and the stdin Stop protocol across APQP workflows. Native discovery checks the signed-in session, identity, filter values, modal dialogs and detail state. | The dispatcher supplies a fixed PROD query. The local policy supplies the SD filter and expected SAP login. The native query checks the SAP login before navigation, accepts home or a clean APQP selection/results page, and stops cooperatively on desktop revocation or parent stdin closure. Agent snapshots are ineligible for edit or cache reuse. |
| Other SAP paths | `Me01NativeRunner` launches its designated engine and uses the same local interaction protocol. `automation_engine_launcher.py` dispatches to fixed bundles, and the renderer has its own existing confirmation and Stop paths. | The bridge calls the APQP query only. The launcher, ME01, existing write controls and Electron UI stay as shipped in v0.3.0. |
| History and recovery | `ExecutionHistoryService` serializes history writes, tracks run/artifact IDs, and protects running and unresolved records during cleanup. RFQ has a separate recovery ledger. | Local APQP history carries the agent job ID. The worker owns a separate outbox for queue writeback and sends only job-safe error codes, the four planned dates and audit IDs. |

## SharePoint list schema

In a future approved tenant, create a blank private list for one worker/operator partition. Use each name below when first creating the column so its internal name matches. Keep the built-in `Title` field, restrict inherited access, and enable version history. Set **Enforce unique values** on `JobId` and `SubmissionKey`, and confirm both are indexed. Index `JobStatus` for the status queries. Use single-select choices and disable fill-in values.

| Internal name | SharePoint type | Owner and rule |
| --- | --- | --- |
| `Title` | Single line of text | Set to `JobId` at creation. |
| `JobId` | Single line of text, indexed, unique | UUID generated by queue ingress. Immutable. |
| `SubmissionKey` | Single line of text, indexed, unique | Lowercase 64-character SHA-256 hex digest of UTF-8 JSON `[tenantId, requesterObjectId, invocationId]` without extra whitespace. Trusted ingress keeps the invocation ID stable across retries. Immutable. |
| `CaseKey` | Single line of text | Business correlation key, 1–64 letters, digits, underscore or hyphen, starting with a letter or digit. Immutable. |
| `Action` | Choice | `QUERY_APQP_PLANNED_DATES`. Immutable. |
| `ParametersJson` | Plain multiline text | Exact object `{"project":"775773"}`, up to 1,024 UTF-8 bytes. Project is 1–32 ASCII letters, digits, underscore, slash or hyphen. Immutable. |
| `RequesterTenantId`, `RequesterObjectId` | Single line of text | Canonical lowercase Entra tenant and object UUIDs stamped by trusted ingress. Immutable. |
| `WorkerId` | Single line of text | Stable lowercase UUID assigned by IT and stamped by trusted ingress. Immutable. |
| `QueuedAt` | Single line of text | Ingress creation time as exact UTC ISO 8601 text such as `2026-11-23T06:10:02.321Z`. Immutable. |
| `JobStatus` | Choice, indexed | `Queued`, `Running`, `Succeeded`, `Failed`, `Review Required`. |
| `ClaimId` | Single line of text | Worker-generated UUID, set on claim. Immutable after claim. |
| `StartedAt`, `CompletedAt` | Single line of text | Same UTC format as `QueuedAt`. Set by the worker on claim and completion. |
| `ResultJson` | Plain multiline text | Present only on success. UTF-8 JSON up to 48,000 bytes. Confirm the tenant column/connector limit with an acceptance test. |
| `ErrorCode` | Single line of text | Empty on success. Use the enumerated failure/review codes in `pah-job-types.ts`. |
| `HubRunId`, `HubHistoryId` | Single line of text | Optional UUIDs that correlate committed queue records with local Hub artifacts and history. |

Require all ingress fields from `Title` through `JobStatus`. Initialize `JobStatus` to `Queued` and leave the worker fields blank. On claim, set only `JobStatus`, `ClaimId` and `StartedAt`. Keep `ClaimId` and `StartedAt` on terminal rows. Turn off rich text and append-only mode for both JSON columns. Store timestamps as text so SharePoint preserves the milliseconds used to compare retried outcomes. The item ID, ETag, `createdBy` and `sharepointIds` are Graph properties supplied by the service.

The successful result has this shape. A `null` field means SAP returned a verified blank. An empty array is valid when SAP returns zero matching records.

```json
{
  "schema": "APQP_PLANNED_FGHM_V1",
  "readAt": "2026-11-23T03:10:45.023Z",
  "records": [
    {
      "apqp": "2000000000",
      "dates": {
        "fPlanDate": null,
        "gPlanDate": "2026-12-02",
        "hPlanDate": "2026-12-08",
        "mPlanDate": "2026-12-15"
      }
    }
  ]
}
```

### Graph adapter configuration

Record the composite Graph site ID (`<hostname>.sharepoint.com,<site-collection-uuid>,<web-uuid>`), the list GUID, the installation worker UUID, the expected requester's Entra tenant and object UUIDs, and the ingress application UUID reported by Graph. Use lowercase UUIDs in policy and list fields. Keep these settings in IT-managed local policy. The adapter targets the global Graph `v1.0` service. [Get SharePoint site](https://learn.microsoft.com/en-us/graph/api/site-get?view=graph-rest-1.0) · [Graph SharePoint IDs](https://learn.microsoft.com/en-us/graph/api/resources/sharepointids?view=graph-rest-1.0)

The adapter validates each item's Graph `sharepointIds` against that scope and requires `createdBy.application.id` to match the approved ingress application. It compares the row's worker/requester fields against local policy and supplies requester identity from that policy. Before deployment, verify that the chosen app-only creation path actually returns that application identity and the required SharePoint metadata. If it does not, keep the bridge disabled until IT approves an ingress path with verifiable provenance. Keep the ingress and worker principals separate and limit list writers to those trusted principals. Graph's creator metadata identifies the writer, so ingress must independently verify the end user's Entra token. [Graph list-item properties](https://learn.microsoft.com/en-us/graph/api/resources/listitem?view=graph-rest-1.0) · [Graph identity sets](https://learn.microsoft.com/en-us/graph/api/resources/identityset?view=graph-rest-1.0)

1. `nextQueued` and `listRunning` use one indexed status filter. Pagination stays on the configured Graph list. Defaults are eight pages, five seconds per authenticated HTTP request, and 30 seconds per queue method. A page limit or invalid row fails the poll without a mutation. Keep the initial partition small and send malformed rows, duplicate keys or repeated limits to the queue administrator for review.
2. `claim` verifies the queued row, exact ETag and unique job/submission keys, then sets Running with one conditional fields PATCH. A 412 loses the claim. A lost, timed-out or incomplete response never authorizes execution. The adapter honors HTTP 429 `Retry-After` across polls with at most two retries per request, and does not retry ambiguous mutations. [Graph list items](https://learn.microsoft.com/en-us/graph/api/listitem-list?view=graph-rest-1.0) · [Graph pagination](https://learn.microsoft.com/en-us/graph/paging) · [Graph conditional updates](https://learn.microsoft.com/en-us/graph/api/listitem-update?view=graph-rest-1.0) · [Graph throttling](https://learn.microsoft.com/en-us/graph/throttling)
3. `complete` verifies the existing claim and conditionally writes the outcome. A retry can accept an identical terminal record after comparing its result, error, timestamps and audit IDs. The local outbox retains evidence after an ambiguous write. An approved restart delivers that checkpoint before examining remaining Running rows, which enter Review Required if they have no checkpoint. One active worker owns a partition. Provision separate worker IDs and lists for separate installations, and stop the old process before replacing a worker.

Run `npm.cmd run test:pah-graph` against the mock transport. It uses synthetic IDs and credentials and never contacts Microsoft Graph, SharePoint or SAP.

## Copilot Studio workflow configuration

1. Enable Microsoft Entra authentication on the agent and publish only to approved channels and users. Configure the submission and status tools for end-user authentication. Keep connection references, environment variables and DLP settings in a managed Power Platform solution. [Agent authentication](https://learn.microsoft.com/en-us/microsoft-copilot-studio/configuration-fundamentals) · [Tool authentication](https://learn.microsoft.com/en-us/microsoft-copilot-studio/configure-enduser-authentication)
2. Add a tool or agent flow named **Query APQP planned dates**. Ask for a case key and project and show the intended read to the user before submission. Set the action literal in the flow. Send only those business inputs to the approved ingestion operation. Use a supported end-user-authenticated connector or existing tenant-controlled service that verifies the caller's Entra token and derives the tenant/object IDs from validated claims. A maker connection, display name, email, conversation variable or free-text identity cannot attest the caller. If the deployed channel cannot propagate verified end-user identity, keep submission disabled there. [Agent flows as tools](https://learn.microsoft.com/en-us/microsoft-copilot-studio/advanced-flow-create)
3. In the trusted ingestion operation, validate action, project, case key and entitlement. Route to the caller's approved operator partition. Generate a job UUID and a stable invocation key once. Create the `Queued` item as the approved ingress application. On a retry collision, look up the unique `SubmissionKey`, verify the original request matches, and return the original job ID. Use authenticated tenant and object claims across submission and retry.
4. Respond promptly with `jobId`, `caseKey` and `Queued`. Use a separate **Get APQP query status** tool taking `jobId`. The trusted read operation verifies requester ownership and current project entitlement before returning status or dates. Show an approved status and the structured date result. Return only the regular error code on failure and direct `Review Required` to the support team for diagnosis. Keep SAP results and credentials out of flow run history and agent telemetry according to tenant policy.

The smallest next deployment is one approved staging list and the two operations above on an existing approved service or connector. Verify list grants, creation provenance, ETag behavior and the Windows operator gate with Fake SAP first. Keep agent tools unpublished and production polling disabled until that acceptance is complete.

## Windows deployment and recovery

1. Use an IT-managed workstation and the approved signed Hub build with its matching bundled engine. Launch as the logged-in, named operator on the supported interactive Windows console. Keep the Hub open and sign in manually to SAP GUI Desktop (VCE/100, Logon entry 949) with that operator's approved SAP account. Use a dedicated idle SAP home or APQP query window. Exclude session 0, service/scheduled noninteractive logons, locked/disconnected desktops, and unsupported remote sessions.
2. Provision one stable worker UUID per installation/operator and bind it to the Windows token SID, accepted tenant/object IDs, SAP login, SD filter and exact project allowlist. Keep policy outside queue data under IT control. The main-process verifier must positively check the process session against the active console, verify an active unlocked interactive input desktop and the approved token SID, and revoke its signal when any condition changes. Electron's lock/suspend events supplement that check. [Active console session](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-wtsgetactiveconsolesessionid) · [Windows desktop model](https://learn.microsoft.com/en-us/windows/win32/winstation/window-station-and-desktop-creation)
3. In a future approved staging bootstrap, create `PahGraphJobQueue` with the policy above, an injected fetch-compatible Graph client and an approved implementation of `PahEntraTokenProvider`. The provider gets a Graph access token for the configured tenant and scope `https://graph.microsoft.com/.default`. Use supported Entra authentication with credentials protected by the OS or an approved broker. Keep tokens out of source, logs, environment variables, child processes and queue fields. The transport must honor cancellation and `redirect: 'error'`. It must expose HTTP 429 and avoid SDK retries on mutations.
4. After the Hub window is ready in `src/main/index.ts`, pass the adapter, existing `apqpDateQuery`, window, configured worker ID, mandatory `verifyOperator` callback and a sanitized poll-error sink to `startPahDesktopBridge`. The callback provides live operator/session approval independently of the list. Keep the returned worker and call `stop()` at the start of shutdown, before waiting for the guided run to stop and checkpoint. Keep the worker exclusive to its partition and deploy the Hub and matching engine together. This wiring is absent from the standard Hub.
5. Run the repository checks before packaging. For an offline exercise run `npm.cmd run test:pah-agent` on Windows with Node, dependencies and Python 3 available. The exercise includes the real APQP query service and child protocol with Fake SAP objects.
6. Limit access to the Hub profile and use managed disk protection. The `pah-job-outbox/<workerId>` directory under Electron user data holds unacknowledged outcomes. Preserve it across updates and restarts. If a transfer, corrupted checkpoint or claim conflict requires operator review, preserve the queue version history, outbox and local run evidence. Confirm that any prior child process has stopped and inspect the SAP window before reauthorizing the desktop. For an abandoned workstation, an administrator can conditionally mark its preserved `Running` job `Review Required` after verifying the old worker is stopped. Do not erase or recycle queue claims. Apply approved retention to terminal jobs and acknowledged evidence.

## IT permissions and production acceptance

| Owner | Permission or approval |
| --- | --- |
| Entra / Power Platform | Approve the agent audience, verified end-user token path, app registrations, conditional access and DLP policies. Approval covers only the selected tenant/site/list and approved data channel. |
| SharePoint | Use application `Lists.SelectedOperations.Selected` with Entra admin consent and an explicit `write` grant on the single list for the dedicated worker and trusted ingress principals. The ingress needs create/read, and the worker needs read and conditional field update. A separate status-only identity needs only `read`, if used. Block end users from editing the list directly. Validate actual access and provenance in staging before enabling the bridge. |
| SAP Basis and business owner | Approve client/server SAP GUI Scripting, `ZMFM050035` display/read authorization, the operator-to-SAP/SD binding, project entitlements and the four fields' release to Copilot. Use individual SAP identities with approved least privilege. |
| Windows endpoint / security | Approve signed app and engine, interactive desktop verifier, trusted distribution and credential storage, outbound Graph/Entra connectivity, restricted user-data ACLs and incident handling. The desktop has no listening endpoint. |
| Data owners and operations | Approve access to status/results, result-size limit, audit retention, Power Platform logging controls and review procedures. |

Before activation, record evidence for each of these checks.

Use a separate administrative session to grant the list permission. Admin consent alone does not grant access to a list. Confirm a worker token for Graph can reach only its target list and that the grant can be revoked. [Graph selected permissions](https://learn.microsoft.com/en-us/graph/permissions-selected-overview) · [Entra client credentials](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-client-creds-grant-flow)

- A verified requester can read only their approved projects. Reject a different tenant, requester, project, SAP account, signed-out SAP, ambiguous windows, modal dialogs, stale policy and unauthorized status lookups.
- Verify the approved Windows console path and fail-closed behavior on lock, sleep, unlock, disconnect, logoff, unsupported session and loss of authorization. Verify cooperative Stop, child exit and recovery with the signed engine. Confirm the SAP account cannot be used across requesters.
- Prove unique ingress under simultaneous create retries, one winner for two conditional claims, correct Graph ETag conflicts, and correct completion after writeback failure or a response lost after commit. Exercise both a restart with a checkpoint and an interruption without one. Confirm no replay and no credentials or tokens in payloads or logs.
- Verify the Hub busy lock and history correlation alongside existing UI workflows. Check that the authorized read sends one query, only reads the approved dates, handles blank and oversized results, and dispatches no save or business-data update. Keep Phase 1 disabled until IT and the SAP business owner sign off.
